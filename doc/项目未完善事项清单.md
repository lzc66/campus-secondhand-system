## 一、P0 必修问题(功能不可用 / 安全灾难)

### 1.1 操作日志 ENUM 与代码写入值不匹配 —— 管理端大量写操作必然 500 且事务回滚
- 【位置】`database/schema.sql:478-480`;`src/main/java/com/campus/secondhand/service/impl/SmtpSettingsServiceImpl.java:263`、`AdminAnnouncementServiceImpl.java:62,83`、`AdminItemManagementServiceImpl.java:119`、`AdminUserManagementServiceImpl.java:75`、`AdminOrderManagementServiceImpl.java:130,146`
- 【问题】`admin_operation_logs` 的 `target_type` ENUM 中没有 `system_setting`;`operation_type` ENUM 中没有 `update_status`、`cancel`、`close`、`create`、`update`。MySQL 8 默认严格模式下插入报 1265 错误,而这些方法均带 `@Transactional`,日志插入失败连带**整个业务回滚**:封禁用户、商品下架/删除、订单取消/关闭、公告新建/编辑、SMTP 配置保存全部失败;SMTP 测试邮件还会出现"邮件已发出但接口返回 500"。由于全部测试都 mock 掉 mapper,该问题在现有测试体系下 100% 无法发现。
- 【建议】扩展 ENUM 覆盖全部实际取值(或改为 VARCHAR + 应用层枚举校验);补一条连库集成测试覆盖"每个管理写操作都成功落一条操作日志"。

### 1.2 JWT 密钥默认值随仓库公开,可离线伪造超级管理员 token
- 【位置】`src/main/resources/application.yml:34`
- 【问题】`secret: ${JWT_SECRET:CampusSecondhandJwtSecretKeyForAdminInit1234567890}`,未设置环境变量时使用仓库内公开的默认密钥。`JwtAuthenticationFilter.java:44-50` 仅凭 claims 中的 `accountType=admin` + `accountId` 查库授权,任何人可用默认密钥签发 `{"accountType":"admin","accountId":1}` 直接成为超级管理员。同类问题:数据库默认口令 `root/123456`(`application.yml:8-10`)。
- 【建议】删除默认值改为强制注入 `${JWT_SECRET}`;`JwtProperties` 加 `@NotBlank` + 最小长度校验;启动时拒绝默认密钥。

### 1.3 默认超管弱口令 + bootstrap"重置后门" + seed 密码回写
- 【位置】`src/main/java/com/campus/secondhand/service/impl/SystemInitServiceImpl.java:27,98-110`;`database/seeds/001_initial_seed.sql:29-41`;`README.md:26-27`
- 【问题】`DEFAULT_ADMIN_HASH` 是 `123456` 的 BCrypt(已实测校验),明文口令同时写在 README 中。更严重的是 `bootstrap()` 检测到管理员已存在时,只要密码/角色/状态与硬编码常量不同,就会**把改过的密码重置回 123456、把被禁用的超管账号重新激活**;seed SQL 的 `ON DUPLICATE KEY UPDATE password_hash = VALUES(...)` 也有同样的重置效果。三者叠加等价于"后台默认无防护,且攻击者可自行恢复默认凭据"。
- 【建议】首次初始化生成随机强密码并强制首次登录改密;bootstrap 改为"存在即跳过",绝不覆盖既有密码/角色/状态;seed 移除密码回写段。

### 1.4 修改密码功能 100% 不可用(前后端字段名不匹配)
- 【位置】`frontend/src/views/user/ProfileView.vue:29-31,47,59-63` vs `src/main/java/com/campus/secondhand/dto/user/ChangePasswordRequest.java:7-10`
- 【问题】前端提交 `{ oldPassword, newPassword, confirmPassword }`,后端 DTO 要求字段名为 `currentPassword` → 每次请求必返回 400 "currentPassword is required",修改密码完全不可用;`confirmPassword` 前端从未校验一致性。
- 【建议】前端字段改为 `currentPassword`,补两次输入一致性校验。

### 1.5 后台看板 4 个图表 / 2 个表格列字段系统性错位,全部空数据
- 【位置】`frontend/src/views/admin/DashboardView.vue:264-295,151-155` vs 后端 VO(`AdminDashboardTrendPointResponse.java` 等);`frontend/src/views/admin/OrdersView.vue:40,69`
- 【问题】前端读取字段与后端 VO 逐项不符:`statDate`→`date`、`createdCount/completedCount/cancelledCount`→`createdOrderCount/completedOrderCount/cancelledOrderCount`、`itemCount`→`count`、`totalUserCount`→`cumulativeUserCount`、`operatorName`→`adminName`、`operationContent`→`operationDetail` → 订单趋势/商品状态饼图/用户增长图恒为空或 Invalid Date,最近动态两列空白;后台订单列表金额列 `orderAmount` 也不存在(实际为 `totalAmount`)。
- 【建议】按 VO 修正字段名;为 `api/admin.ts` 的 dashboard 接口补类型(当前全部返回 `any`,见 5.3.1)。

### 1.6 学生证等敏感文件匿名可下载 + 上传校验可绕过(存储型 XSS)
- 【位置】`src/main/java/com/campus/secondhand/config/WebMvcConfig.java:21-27`;`config/SecurityConfig.java:47`;`service/impl/LocalFileStorageService.java:119-142`
- 【问题】`/uploads/**` 匿名映射整个存储根目录,`student-cards/`(学生证影像,含真实姓名学号的 PII)与商品图在同一公开根下,任何人拿到 URL 即可下载;`validateImage` 只信任客户端自报的 `Content-Type`、`resolveExtension` 直接取原始文件名后缀且无白名单 → 可上传 `xxx.html`/`xxx.svg` 落盘,经同源静态目录直出构成存储型 XSS。
- 【建议】学生证移出公开目录改为鉴权下载接口(校验管理员或本人)+ 查看审计;扩展名白名单 + 文件头 magic bytes 校验 + 落盘时统一改写扩展名;响应加 `X-Content-Type-Options: nosniff`。

### 1.7 下单库存检查存在竞态,可超卖
- 【位置】`src/main/java/com/campus/secondhand/service/impl/UserOrderServiceImpl.java:79-85,114,396-401`
- 【问题】"读库存 → Java 侧判断 → 整行 `updateById` 写回",`items` 表无 `version` 列、全工程无 `@Version`、无 `SELECT ... FOR UPDATE`。两个并发请求可同时读到 `stock=1` 各自通过校验双双扣减 → 超卖;`stock` 为 `INT UNSIGNED`,减法下溢在 DB 层报错变成 500 而非业务拦截。
- 【建议】改为条件原子扣减:`UPDATE items SET stock = stock - ? WHERE item_id = ? AND stock >= ? AND status = 'on_sale'`,按影响行数判断失败;或加 `@Version` + 乐观锁插件。

### 1.8 完成/取消订单会把已下架/已删除商品强制改回"在售"(软删除语义被破坏)
- 【位置】`UserOrderServiceImpl.java:205-213,403-408`;`service/impl/AdminOrderManagementServiceImpl.java:164-171`
- 【问题】`completeOrder`/`restoreItemStock`/管理员取消订单均**无条件**把商品状态置回 `ON_SALE`。真实触发链:①卖家下架商品 → 买家完成此前订单 → 商品被静默重新上架,下架意图被推翻;②卖家软删商品(`status=DELETED` + `deletedAt=now`)→ 买家完成/取消订单 → `status` 被改回 `ON_SALE` 但 `deletedAt` 仍非空,而公开列表只按 `status` 过滤(`PublicItemServiceImpl.java:85` 无 `deletedAt IS NULL` 条件)→ **已删除商品重新公开可见**。
- 【建议】状态回写必须带前态判断(仅 `RESERVED`/`SOLD` 可回退 `ON_SALE`);所有公开查询补 `.isNull(Item::getDeletedAt)`;恢复库存前校验 `deletedAt == null`。

### 1.9 演示模式形同虚设 + 演示数据埋入可登录弱口令账号且不可撤销
- 【位置】`service/impl/AdminDemoModeServiceImpl.java:88,91,216-219,306-320`;`controller/publicapi/PublicDemoModeController.java:20-23`
- 【问题】`demo_mode_enabled` 全链路只用于前端展示,没有任何服务端拦截:无需开启即可注入演示数据,关闭后演示数据与演示账号依然完全有效;`seedDemoData` 直接创建 4 个 `ACTIVE` + 口令 `123456` 的用户(绕过注册审核),`OPERATOR` 角色即可触发,系统无任何清理接口;前端演示标记正则 `/^\[(婕旂ず|Demo)\]/`(`ItemCard.vue:38`、`ItemDetailView.vue:234`)中的 `婕旂ず` 是"演示"的编码乱码,永远不命中,答辩演示时角标失效。
- 【建议】开关真正接入(seed 前置校验、公开查询按开关过滤、演示账号限制登录);提供 `clearDemoData` 清理接口;演示账号用随机一次性口令;修正乱码正则并抽为常量。

### 1.10 下单成功后跳转到不存在的路由 → 白屏
- 【位置】`frontend/src/views/public/ItemDetailView.vue:344`;`frontend/src/router/index.ts`(全表)
- 【问题】`router.push('/orders')`,但路由表只有 `user/orders`,且全项目没有 `/:pathMatch(.*)*` 404 兜底路由 → 用户下单成功后进入空白页,体验灾难。
- 【建议】改为 `router.push({ name: 'orders' })`;补 404 兜底路由。

## 三、功能未完成 / 半成品

### 3.1 订单状态机不闭环
- 【位置】`service/impl/UserOrderServiceImpl.java:78-117,221-243`;`enums/OrderStatus.java`、`OrderType.java`、`PaymentMethod.java`
- 【问题】①`DELIVERING` 状态买家既不能取消也不能关闭(仅管理员可关);②`OrderType.OFFLINE_RECORD`(线下成交记录)在全项目从未被创建,`ONLINE_COD` 被硬编码;③没有独立"支付"环节,`paymentStatus` 只在完成订单时由 `UNPAID` 直接置 `PAID`,无支付失败/退款任何状态。
- 【建议】补齐或明确禁止 `DELIVERING → CANCELLED`;实装或删除 `OFFLINE_RECORD`;若纯 COD 模式需在文档中明确说明。

### 3.2 下单不校验商品交易方式,纯线下商品可在线下单
- 【位置】`service/impl/UserOrderServiceImpl.java:298-307`
- 【问题】`getPurchasableItem` 只校验 `status==ON_SALE` 与 `stock>0`,完全忽略 `ItemTradeMode.OFFLINE`。
- 【建议】离线交易商品下单时抛业务错误,或明确线上线下双通道规则。

### 3.3 通知双通道只实现一半
- 【位置】`service/impl/NotificationServiceImpl.java:76-146`;`service/impl/ItemCommentServiceImpl.java`、`UserOrderServiceImpl.java`(零调用)
- 【问题】①公告发布只插站内信、完全没有邮件通道,且一次全量加载 ACTIVE 用户逐条 insert;②注册驳回只建 EMAIL 记录且 `receiverUserId=null`,站内信中心永远看不到;③`ORDER_UPDATE`、`COMMENT_REPLY` 两个业务枚举**只出现在演示种子数据里**,真实业务流程零调用——订单确认/发货/完成/取消不通知对方、卖家回复评论不通知评论人;④邮件同步发送在事务内、无异步无重试,`PENDING`/`FAILED` 记录永久滞留且失败原因不记录。
- 【建议】补齐订单状态与评论回复通知;公告邮件改为 `@Async` + 分批扇出 + `AFTER_COMMIT` 事件;新增定时重试任务。

### 3.4 评论功能不闭环
- 【位置】`service/impl/ItemCommentServiceImpl.java:88-161,194-221`
- 【问题】`HIDDEN`/`DELETED` 状态全项目无写入路径(无删除/隐藏/举报处理);`replyComment` 强制仅卖家可回复,买家无法追问;回复列表无分页;更严重的是**对"回复"再回复会产生永不显示的孤儿评论但 `comment_count` 照加**,导致商品评论数虚高。
- 【建议】补评论删除(作者本人)与管理员隐藏接口;回复回复规范化到根评论;补评论数对账。

### 3.5 推荐系统是加权规则打分,并非协同过滤,且中文分词失效
- 【位置】`service/impl/UserRecommendationServiceImpl.java:94-210,292-339`
- 【问题】算法为"行为权重累加 + 关键词子串命中 + 热度分"的规则引擎,不是论文口径中的协同过滤;`COLLABORATIVE_FILTERING`/`MANUAL` 两个 reasonCode 永不产生(死枚举);中文分词用 `split("[^字母数字]+")` 会把中文标题切成一个超长 token,中文关键词命中基本失效。
